# Защита основной ветки

[English](../BRANCH_PROTECTION.md) · [Основная документация](../../README.ru.md)

Цель настройки — репозиторий `Artem7898/ai_code_reviewer`, основная ветка `master`.
Файл [`.github/branch-protection.json`](../../.github/branch-protection.json)
содержит предлагаемую конфигурацию GitHub API. **Публикация этого файла сама по
себе не включает защиту.** Защита действует только после успешной записи через
API и контрольного чтения либо после сохранения аналогичных настроек
администратором в GitHub.

Минимальные требования:

- Pull request с одним одобрением; новые коммиты отменяют прежние одобрения.
- Успешная проверка `validate` из `.github/workflows/ci.yml` и актуальность ветки.
- Разрешение обсуждений ревью и применение правил к администраторам.
- Запрет принудительной отправки коммитов и удаления ветки.

Одно обязательное одобрение требует другого участника с правом ревью. Автор
pull request не может одобрить собственные изменения. Если репозиторий ведёт
один человек, сначала добавьте подходящего рецензента.

## Проверка и применение

Нужны Python 3.14 и установленный GitHub CLI (`gh`), авторизованный под учётной
записью с правами администратора репозитория. Установка GitHub App или
fine-grained токен, используемый CLI, также должны иметь разрешение репозитория
**Administration: read** для чтения защиты и **Administration: write** для её
изменения. Права администратора учётной записи сами по себе не предоставляют
эти разрешения интеграции. Не указывайте токен в команде, файлах проекта или
сообщениях чата. Нужен доступ HTTPS к `api.github.com`.

```bash
# Прочитать сведения о репозитории и текущую защиту, вывести итоговый проект правил.
# По умолчанию выполняются только запросы GET.
python scripts/protect_branch.py

# Явно записать правила, прочитать их обратно и проверить результат.
python scripts/protect_branch.py --apply
```

Перед записью скрипт проверяет точное имя репозитория, основную ветку и права
администратора. Сохраняются прежние обязательные проверки и их привязки к GitHub
Apps, более высокое число одобрений, ревью владельцев кода, одобрение последней
отправки, ограничения отмены ревью, списки обхода правил, ограничения отправки и
другие известные параметры защиты. При неизвестных параметрах скрипт прекращает
работу, чтобы не потерять действующие требования. Подпись коммитов настраивается
отдельным API: скрипт её не меняет и проверяет сохранение прежнего требования.
Наборы правил репозитория и параметры слияния не изменяются.

При публикации API был доступен, а сведения о репозитории подтверждали права
администратора. Метаданные ветки подтвердили `protected: false`, однако чтение
`branches/master/protection` и попытка применить сохранённую политику завершились
HTTP 403: `Resource not accessible by integration`. Для запроса чтения заголовок
`X-Accepted-GitHub-Permissions` указал требуемое разрешение
`administration=read`. Текущая интеграция не может прочитать или применить правила;
попытка записи не включила защиту.
Повторно авторизуйте GitHub-интеграцию через безопасный интерфейс с разрешениями
Administration read/write для этого репозитория либо используйте настройки
GitHub, описанные ниже. Передавайте учётные данные только через защищённую
авторизацию платформы или настройки среды. После этого повторите проверку без
`--apply`, затем примените правила.

Если API заблокирован, разрешите `api.github.com` в сетевых настройках облачной
среды, сохраните и примените настройки, затем повторите команду. Изменение
черновика списка доменов ещё не означает, что текущая машина получила доступ.
Ошибка чтения не приводит к записи правил. Файл JSON и вывод пробного запуска
не подтверждают, что защита уже включена.

Альтернативный путь: администратор открывает GitHub **Settings → Branches → Add
classic branch protection rule**, выбирает `master` и включает требования выше.
Проверьте результат в GitHub и повторите запуск скрипта без `--apply`, когда API
и необходимые разрешения интеграции станут доступны. Доступность функций зависит
от видимости репозитория, тарифного плана и правил организации.

Выполните workflow `validate` хотя бы один раз, чтобы GitHub распознал имя
проверки. После включения защиты отправляйте последующие изменения через pull
requests. После первой публикации проверьте результат Actions и настройки защиты.
